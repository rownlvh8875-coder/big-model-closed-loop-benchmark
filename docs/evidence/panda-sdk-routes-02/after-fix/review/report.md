## Important issues

### I1 — Tar extension metadata bypasses the new save parser's metadata and allocation bounds

**Locations:** `scripts/panda_sdk_routes_archive.py:165` (outer tar parser), `scripts/panda_sdk_routes_archive.py:101` (layer tar parser), and `scripts/panda_sdk_routes_archive.py:176` (incomplete metadata accounting).

`tarfile` consumes PAX/global-PAX/GNU extension records internally before yielding an ordinary member. The outer parser passes the raw file directly to `tarfile`; therefore its later member/JSON checks do not limit extension-header allocation or account for those bytes. The layer parser limits aggregate decoded bytes, but its chunked reader does not prevent `tarfile` from assembling a large extension record internally. Both paths accept a valid image with a 17 MiB global-PAX comment, exceeding even `MAX_METADATA_BYTES=16 MiB` (and the specification's tighter metadata budget).

**Reproduction:** Run the retained, data-only diagnostic:

```sh
cd /workspace/big-model-closed-loop-benchmark
/workspace/.cloud-tools/stage7/first-divergence-cpu-replay/bin/python -B /tmp/panda-review-pax.py
```

It uses `make_save` to construct a tiny handwritten image fixture, prepends a correctly encoded global-PAX `comment` containing 17 MiB of text, and calls `inspect_save_archive`. It repeats the case inside a layer with the config diffID correctly bound. Actual output:

```text
PAX bytes 17825810 metadata limit 16777216
result DOCKER_SAVE_STRUCTURE_VERIFIED
layer result DOCKER_SAVE_STRUCTURE_VERIFIED
```

**Impact:** The advertised bounded data verifier can allocate and parse extension metadata up to a substantial fraction of its 2 GiB archive / 3 GiB decoded-layer limits before the intended metadata checks run. A malformed or oversized retained archive can exhaust process memory or consume disproportionate time rather than reject within the declared metadata budget. This does not establish native execution or falsify the SDK hash; it is a material resource-boundary failure in newly introduced executable validation code. The export-only oversized-PAX unit test does not exercise either affected save-parser path.

**Recommendation:** Enforce extension-record size, aggregate metadata, and record-count limits before `tarfile` allocates/parses them, at both outer and layer boundaries. Include PAX/global-PAX and GNU long-name/link forms; ensure compressed layers receive the same checks. Add regression fixtures for valid oversized extension metadata (not only truncated headers), aggregate smaller extension records, and the existing valid legacy image format. Preserve the old immutable parser.

### I2 — The fake-Docker CPU test still requires the exact managed Cloud tool installation

**Location:** `tests/test_panda_sdk_routes_image.py:68` (with calls at line 69), invoking `scripts/panda_sdk_routes_image.py:102`.

The test replaces `DOCKER` with a handwritten CPU child, but leaves `inputs.verify_tool_files(inputs.tool_profile())` active. Consequently it verifies every production profile entry before the fake child can start, including Cloud-specific interpreter/private-sysroot paths and exact GCC/binutils/Docker bytes. A standard checkout on GitHub's `ubuntu-latest` runner cannot supply those exact managed workspace files. The repository CI workflow runs full discovery at `.github/workflows/ci.yml:18`, so this new test introduces a CI failure unrelated to the endpoint/timeout behavior it intends to test.

**Reproduction:** `/tmp/panda-review-ci-profile.py` runs the existing test with only the profile's managed-Docker path redirected to an absent `/tmp` path, modeling an unavailable managed tool while preserving the fake child. It reports **1 test, 1 error**, a `FileNotFoundError` in `verify_tool_files` before the child executes. The same boundary rejects a differing compiler hash. The parent flagged this portability concern during the review; I independently inspected the workflow and reproduced the failure.

**Impact:** The local 34-test/full-suite pass is dependent on this one Cloud host and does not predict a passing required PR unit-test job. Ordinary CPU-only checkouts fail despite having everything needed to execute the fixture.

**Recommendation:** Isolate the production profile verifier at this unit-test boundary (for example, a test-local mock with invocation assertions, or a complete fixture profile bound to CPU tools). Keep the actual handwritten child execution and endpoint/timeout assertions. Preserve production tool verification; do not weaken the real image builder or merely skip the test on CI. Add a regression demonstrating the CPU test does not access the managed profile paths.
